Others need active effort every week to deliver value. Know which is which. These require human effort every single day. The top six are technical infrastructure — configure them once and they work. 1. Shadcn/UI Set and forget — no ongoing action required PRE-LAUNCH LAUNCH DAY POST-LAUNCH (ONGOING) Install components and set brand color. After that, just use the components in every Claude Code UI prompt. Nothing — already done. When building new features, tell Claude Code to use shadcn components. Add new components as needed with: npx shadcn@latest add [component] How to Use It in Claude Code Prompts Shadcn&apos;s value is that Claude Code uses it automatically once installed. The only thing you need to do is mention it in your prompts so Claude Code reaches for shadcn components instead of building raw HTML. ACTION: Include this line in every UI-building Claude Code prompt: &apos;Use shadcn/ui components for all UI elements.&apos; Adding New Components The initial install covers the core components. As you build features you may need additional ones. Run in terminal when needed: npx shadcn@latest add calendar (for date pickers in the booking form) npx shadcn@latest add command (for searchable dropdowns in listing filters) npx shadcn@latest add toast (for booking confirmation notifications) npx shadcn@latest add avatar (for outfitter profile photos) npx shadcn@latest add table (for the Scout draw odds table) Don&apos;t manually edit files inside the shadcn components folder — updates will overwrite your changes. Customize through the CSS variables in globals.css instead. 2. Zod Set and forget — add schemas as new forms are built PRE-LAUNCH LAUNCH DAY POST-LAUNCH (ONGOING) Core schemas created (signUp, listing, booking, review, scoutQuery). Test each by running safeParse with invalid data. Nothing new — schemas are working. Every time a new form is added to the platform, a new Zod schema goes into lib/validations/index.ts before any other code is written for that form. The Rule Every form that writes to Supabase gets a Zod schema first. No exceptions. The Claude Code prompt pattern is always: &apos;Before building the form, create a Zod schema for it in lib/validations/index.ts, then use it in the server action to validate before any database operation.&apos; Forms Still Needing Schemas As you build out the platform, these forms will need schemas added: Outfitter profile edit form — business name, bio, success rate, guide ratio Availability calendar — dates, blocked periods, max party size per date Password reset / email change forms Scout priority weights form — all sliders must be 1–5 integers Admin outfitter verification form — license number, verified boolean Testing Schemas When you add a new schema, test it immediately with this pattern in the Claude Code prompt: &apos;After creating the schema, write 3 test cases: one with valid data that should pass, one missing required fields that should fail, one with wrong data types that should fail. Log the results.&apos; 3. Sentry Reactive — configure once, respond to alerts as they happen PRE-LAUNCH LAUNCH DAY POST-LAUNCH (ONGOING) Run a deliberate pre-launch error sweep: manually trigger every critical flow and watch Sentry for unexpected errors before real users hit them. Set up Sentry alert routing — make sure errors go to your phone, not just email. Triage every new error within 24hrs. Fix P0 errors (booking fails, payment errors) same day. Review the Issues list weekly. Pre-Launch Error Sweep — Do This Before Going Live Before any real users touch the platform, deliberately test every flow that involves money or data and watch Sentry for errors you didn&apos;t expect. This is the most valuable thing you can do with Sentry pre-launch. Log in as a hunter. Try to book a listing with invalid dates. Sentry should NOT fire — this should be caught by Zod before hitting the server. Log in as a hunter. Start a Stripe checkout and abandon it halfway. Check Sentry for any uncaught errors in the checkout flow. Log in as an outfitter. Submit a listing with a missing required field. Confirm the error is caught cleanly without a 500. Hit the Scout page with no draw_odds data in the database. Confirm it shows &apos;no data&apos; gracefully, not a crash. Trigger a real Stripe test payment using card 4242 4242 4242 4242. Watch Sentry — there should be zero errors. Try all of the above on mobile. Mobile layouts often surface different JS errors. Alert Configuration By default Sentry emails you. Pre-launch you want faster notification. In Sentry dashboard: Settings → Notifications → enable Slack or SMS alerts for new issues Create an Alert Rule: &apos;Notify me immediately when a new issue occurs in the checkout or booking flow&apos; Create a second Alert Rule: &apos;Notify me if error rate exceeds 5 errors/hour&apos; — this catches cascading failures fast Weekly Triage Routine Every Monday, spend 10 minutes in Sentry → Issues. For each open issue: P0 — booking fails, payment errors, auth broken: fix same day P1 — Scout crashes, listing page errors: fix within the week P2 — minor UI errors, non-critical flows: batch and fix monthly Noise — ResizeObserver, bot traffic errors: mark as ignored Don&apos;t let Sentry become a graveyard of ignored errors. Unreviewed issues pile up and you stop noticing when a real P0 appears. 10 minutes weekly prevents this. 4. Google Search Console Active — weekly 15-minute review PRE-LAUNCH LAUNCH DAY POST-LAUNCH (ONGOING) Submit sitemap. Manually request indexing for your 5 most important pages. Fix any crawl errors immediately. Submit sitemap. Verify all key pages are being crawled. Set up email alerts for coverage issues. Weekly review of queries, impressions, and crawl errors. Submit new blog articles for indexing the day they publish. Pre-Launch Actions — Do These in Order Go to GSC → Sitemaps → Submit sitemap → enter https://huntscout.com/sitemap.xml → Submit Go to URL Inspection → enter https://huntscout.com → click &apos;Request Indexing&apos; Repeat for: /listings, /scout, /blog, /outfitters/apply Go to Coverage report — fix any pages marked as errors or excluded before launch Enable email alerts: Settings → Email preferences → turn on all Coverage and Sitemaps notifications Weekly Review Routine — 15 Minutes Every Monday GSC data updates with a ~3 day lag. Monday reviews capture the prior week accurately. GSC Section What to Check Action if Bad Performance → Queries Which keywords are getting impressions? Are any &apos;guided hunt [state]&apos; or &apos;draw odds [species]&apos; queries appearing? Write a blog article targeting that keyword this week Performance → Pages Which pages are getting clicks? Is /scout getting organic traffic? Add internal links from blog posts to Scout Coverage → Error Any pages returning 404, 500, or blocked by robots.txt? Fix immediately — errors hurt overall site ranking Coverage → Valid Is the count growing week over week as you publish content? If stagnant, check sitemap is updating correctly Sitemaps Is the sitemap showing 0 errors? Is the page count accurate? Rebuild sitemap if count is wrong When You Publish a New Blog Article Every time a new article goes live, immediately go to GSC → URL Inspection → enter the article URL → Request Indexing. This gets it into Google&apos;s index within hours instead of weeks. ACTION: Set a recurring Monday calendar block: &apos;15 min — GSC + GA4 review&apos;. This is the single most important SEO habit to build. 5. Google Analytics 4 Active — weekly funnel review PRE-LAUNCH LAUNCH DAY POST-LAUNCH (ONGOING) Verify all 5 custom events are firing correctly using GA4 DebugView. Mark &apos;booking_completed&apos; as a conversion. Check Realtime report shows first user sessions. Confirm events fire on real actions. Weekly review of Scout funnel (query → upgrade click → subscribe) and booking funnel (listing view → booking started → completed). Pre-Launch Event Verification Before launch, verify every custom event fires correctly using GA4 DebugView: Enable debug mode: add ?_ga_debug=1 to any URL, or install the GA Debugger Chrome extension Go to GA4 → Configure → DebugView — you&apos;ll see events in real time as you trigger them Click a listing → confirm listing_viewed fires with correct listing_id, species, state, price Start a booking → confirm booking_started fires with correct listing_id, booking_type Complete a test booking → confirm booking_completed fires with correct total_price Run a Scout query → confirm scout_query_run fires with state, species, points Click the Scout upgrade CTA → confirm scout_upgrade_clicked fires Mark booking_completed as a Conversion In GA4 → Configure → Events → find booking_completed → toggle &apos;Mark as conversion&apos; to ON. This makes it show up in your Conversions report and lets you measure which traffic sources drive actual bookings. Weekly Funnel Review — Run This Every Monday Alongside GSC Funnel What to Measure Healthy Benchmark Booking funnel Listing views → booking_started → booking_completed 10%+ of listing views start a booking, 50%+ of those complete Scout funnel scout_query_run → scout_upgrade_clicked → subscription 5%+ of free queries click upgrade, 10%+ of those subscribe Acquisition Which traffic source drives booking_completed most? Organic (GSC content) should grow month over month Top listings Which listing pages get the most views? Top 3 listings should have 3x the views of average Engagement Average session duration on /scout If under 90 seconds, the free tier isn&apos;t showing enough value Setting Up the Booking Funnel Report In GA4 → Explore → Funnel Exploration → create a funnel with these steps in order: listing_viewed → booking_started → booking_completed. This shows you exactly where hunters drop off. Save this report and check it weekly. GA4 data takes 24-48 hours to fully process. The Realtime report is instant but Explore reports lag. Don&apos;t make decisions off data less than 2 days old. 6. Vercel Analytics + Speed Insights Passive monitor — check after every deploy PRE-LAUNCH LAUNCH DAY POST-LAUNCH (ONGOING) Enable in Vercel dashboard. Nothing else needed until the site deploys. Verify data is populating in the Vercel dashboard after first real traffic. Check Speed Insights after every significant deploy. If a page&apos;s LCP (Largest Contentful Paint) degrades, investigate before it hurts SEO. What to Watch Vercel Analytics is simpler than GA4 — no event tracking, just page views and performance. Its value is speed and simplicity. You check it when something might be wrong, not on a fixed schedule. Metric Where to Find It When to Act Page views by route Analytics → Pages If /scout or /listings suddenly drops, check for broken routes or indexing issues LCP (load time) Speed Insights → by page If any page exceeds 2.5s LCP, it&apos;s hurting SEO — investigate the deploy that caused it CLS (layout shift) Speed Insights → by page Scores above 0.1 mean UI is jumping around — bad UX and bad for SEO FID/INP (interactivity) Speed Insights → by page Above 200ms on /listings search means the filter UI is too slow Top traffic pages Analytics → Pages ranked by views If a blog article suddenly spikes, it&apos;s ranking — write a follow-up on the same topic Post-Deploy Checklist After every significant deploy (new feature, major UI change, new blog article), check these in Vercel: Speed Insights → compare LCP before and after deploy for the pages you touched Analytics → verify the new page/route is showing up in the Pages list If LCP degraded: check for unoptimized images, heavy JavaScript bundles, or missing Next.js Image component usage ACTION: Use Next.js Image component (&lt;Image&gt;) for ALL outfitter photos and listing images. Vercel optimizes these automatically. Raw &lt;img&gt; tags will tank your Speed Insights scores. 7. Cal.com Active — daily, every outfitter call needs to be booked and logged PRE-LAUNCH LAUNCH DAY POST-LAUNCH (ONGOING) Add the Cal.com link to every outreach message, your email signature, and the /outfitters/apply page. Include in your launch announcement. Add to your HubSpot email templates. Every booked call gets logged in HubSpot after it happens. No exceptions. Where the Cal.com Link Goes The booking link should appear in these places — set these up before any outreach starts: Your email signature: &apos;Book a 30-min HuntScout intro call: [CAL LINK]&apos; Every outreach follow-up text and email (see Tally section templates above) The /outfitters/apply page — already embedded via the Claude Code prompt Your HubSpot contact email templates The confirmation email Tally sends after a form submission The Call Agenda — Every Outfitter Onboarding Call Having a consistent agenda makes these calls efficient and ensures nothing gets missed: Minutes 0–5: Intro — how HuntScout works, what the Founding Outfitter Program includes Minutes 5–15: Their operation — what species, what units, success rates, group sizes, lodging Minutes 15–25: Build their listing live on the call — share your screen, fill in the form together Minutes 25–30: Questions + next steps — photo submission, what happens when they get a booking After Every Call Immediately after the call (while it&apos;s fresh): Log the call outcome in HubSpot — what was discussed, any concerns they raised Move them to the correct pipeline stage (Onboarding, Live, or Not Interested) If they&apos;re proceeding: send a follow-up email with photo submission instructions and a link to review their draft listing If they need to think: set a follow-up task in HubSpot for 5 days out Photo Submission Instructions to Send Post-Call &apos;To complete your listing we need: 5–10 high-quality photos (minimum 1920px wide), your outfitter license number, and your state-verified guide license. You can email these to [EMAIL] or reply to this message. Once we have everything your listing goes live within 48 hours.&apos; Most outfitters will say yes on the call and then go quiet. The follow-up is where listings get built or stall. Set a HubSpot reminder for 48hrs after every call if you haven&apos;t received their photos. 9.
